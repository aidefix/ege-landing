# Лендинг курса подготовки к ЕГЭ по русскому языку

**Тип проекта:** одностраничный сайт частного преподавателя
**Роль:** тимлид, фронтенд-разработка, интеграции
**Команда:** дизайнер, копирайтер-методист, верстальщик-прототипировщик, фронтенд

---

## О проекте

Боевой одностраничник для частного преподавателя ЕГЭ по русскому языку. Аудитория делится на два непересекающихся сегмента: родители 11-классников (платят, но не выбирают репетитора) и сами ученики (выбирают, но не платят). Задача сайта — конвертировать обе группы в одну заявку на бесплатную диагностику.

## Задача проекта

Собрать одностраничный сайт с интерактивными блоками (тренажёр, разбор сочинения, калькулятор тарифа), формой заявки с доставкой в два канала (Telegram и email), полной SEO-разметкой и юридической базой под 152-ФЗ. Сайт должен быть визуально узнаваемым — стилистика бумажной тетради со стикерами и «скотчем», без сине-фиолетовых градиентов и стоковых фото, которые размывают тему в общей массе EdTech-сайтов.

## Требования

- Серверный рендер и SEO-разметка (JSON-LD, sitemap, OpenGraph)
- Один запрос на весь сайт — отправка заявки; никаких SPA-роутеров и стейт-менеджеров
- Валидация формы одной схемой на клиенте и на сервере
- Защита от спам-ботов без капчи (капча снижает конверсию)
- Доставка заявки в Telegram и email параллельно, с фолбэком, если один канал упал
- Юридические страницы: политика, согласие на обработку данных, публичная оферта
- Метрика с целями на все ключевые действия (Яндекс.Метрика, не GA — аудитория российская)
- Полная доступность с клавиатуры и скринридеров
- Один брейкпоинт — 840px

## Стек

Next.js 16 (App Router) · React 19 · TypeScript strict · Tailwind v4 (CSS-first, `@theme`) · Radix UI (только Accordion) · Zod · Nodemailer · Яндекс.Метрика

## Этапы работ

### 1. Бриф и правила проекта

Разложили аудиторию на два сегмента и вывели tone of voice: спокойный, конкретный, цифры вместо прилагательных, без гарантированных «100 баллов» и восклицательных знаков в заголовках, обращение только на «вы».

**Проблема.** На первых прогонах текстов копирайтер по инерции скатывался в шаблонный «инфобиз»: «взорви свой результат», «гарантируем 90+», эмодзи в кнопках. Родители читают такое и уходят — им нужны цифры и логика.

**Решение.** Записали жёсткие правила проекта в отдельный файл-инструкцию. Каждый текст и каждая карточка проходили по чек-листу: «Гарантий баллов нет — есть статистика», «Никаких сине-фиолетовых градиентов, glassmorphism, мягких теней, стоковых фото». Правки шли быстрее: спор сводился к «нарушает пункт X», а не «мне не нравится».

### 2. Визуальный прототип-эталон

Дизайнер собрал один HTML-файл с полным дизайном лендинга — палитра, шрифты, композиция, стикеры, «скотч», текстовый декор (звёздочки, галочки, крестики вместо иконок). Прототип стал утверждённым визуальным контрактом.

**Проблема.** Классический риск — команда начинает копировать HTML прототипа в компоненты «как есть», и через две недели проект превращается в неподдерживаемую портянку с инлайновыми стилями.

**Решение.** Ввели правило: «Прототип — референс визуала, не исходник». Разделили ответственность:

- токены дизайна — в `globals.css` через `@theme`;
- разметка — в компонентах `src/components/sections/` и `src/components/ui/`;
- контент — в типизированных модулях `src/lib/`.

После запуска прототип «умер», код остался чистым.

### 3. Архитектура

Приняли осознанное «нет» модному стеку:

- нет TanStack Query — запрос ровно один;
- нет стейт-менеджера — состояние живёт в четырёх клиентских компонентах;
- нет FSD — избыточно для одностраничника;
- нет библиотеки иконок — используем текстовые глифы (`✦`, `✓`, `×`).

Серверные компоненты по умолчанию. `"use client"` только там, где нужна интерактивность: тренажёр, разбор сочинения, выбор тарифа, форма заявки.

### 4. Дизайн-система на Tailwind v4

Перешли на CSS-first подход: нет `tailwind.config.js`, все токены — в `@theme` внутри `globals.css`. Пять «предметных» цветов для модулей курса, чтобы прогресс-бар тренажёра, чипы задач ЕГЭ и заливка карточек программы были синхронны без вбитых hex-ов в JSX.

**Проблема.** Тени в дизайне — только жёсткие, без размытия (стилистика бумажного плаката). Стандартные утилиты Tailwind не подходят — они размывают.

**Решение.** Определили собственный набор `--shadow-hard-*` и `--shadow-ink-*` как CSS-переменные. Tailwind v4 автоматически сгенерил классы `shadow-hard-md`, `shadow-ink-lg` и т.д. — без плагинов.

**Проблема.** Стикеры и «скотч» намеренно выходят за край листа с поворотом. На мобильных это создавало горизонтальный скролл в 5–10 пикселей.

**Решение.** `overflow-x: clip` на `html` и `body`. Не `hidden`, а именно `clip` — он не блокирует `position: sticky` у вложенных элементов.

### 5. Контент как данные

Весь контент — типизированные структуры в `src/lib/`. Тексты, номера заданий ЕГЭ, программа модулей, вопросы тренажёра, ошибки в разборе сочинения — всё вынесено из JSX. Копирайтер-методист правит `.ts`-файлы в отдельной ветке, не трогая компоненты; мердж-конфликтов с фронтендом почти нет.

**Проблема.** Разбор сочинения — интерактивный: пять ошибок в тексте, каждая кликается, справа выезжает объяснение. Первая версия хранила текст с ошибками как JSX — было невозможно править без разработчика.

**Решение.** Модель «сегментов»:

```ts
export type EssaySegment =
  | { readonly kind: "text";  readonly text: string }
  | { readonly kind: "error"; readonly id: EssayErrorId };
```

Компонент рендерит массив, ошибки — отдельным реестром с полями `was`, `fix`, `rule`, `why`. Методист меняет тексты за 10 секунд, дизайн не ломается.

### 6. Интерактивный тренажёр

Пять вопросов из разных модулей ЕГЭ, прогресс-полоска, вердикт после каждого ответа с разбором, финальный экран с рекомендацией «где просело» на основании ключа модуля.

**Проблема.** Прогресс-бар должен окрашиваться в цвет соответствующего модуля курса — жёлтый для ударений, синий для орфографии и т.д. Но Tailwind в продакшене вырезает классы, собранные динамически: `bg-m${key}` работать не будет.

**Решение.** Хелпер `moduleBg(key)` возвращает статичный класс из фиксированной таблицы. Все возможные классы присутствуют в исходнике явно — Tailwind их видит, прод-билд не ломается.

**Проблема.** Доступность. Прогресс-бар из декоративных `<div>` — невидим для скринридеров.

**Решение.** `role="progressbar"` с `aria-valuemin/max/now`, у вердикта — `role="status" aria-live="polite"`. NVDA и VoiceOver зачитывают разбор сразу после клика.

### 7. Форма заявки и API

Одна форма на всю страницу. Клиент валидирует Zod-схемой, чтобы показать ошибки у полей. Сервер валидирует той же схемой — потому что клиенту верить нельзя. Роут `/api/lead`: rate-limit → парсинг → валидация → honeypot → уведомления в Telegram и SMTP параллельно через `Promise.allSettled`.

**Проблема.** Спам-боты. На dev-домене за первые часы поймали десятки автоотправок.

**Решение — три слоя защиты без капчи:**

1. **Honeypot-поле `company`.** Скрыто через `absolute; left: -9999px`, `tabIndex={-1}`, `aria-hidden`. Люди не видят, боты заполняют. Сервер отвечает `ok: true`, но заявка не уходит никуда.
2. **Time trap.** Клиент замеряет миллисекунды от монтирования формы до отправки. Меньше трёх секунд — отказ, живой человек так быстро не заполнит.
3. **Rate-limit по IP.** Три запроса за десять минут, `Map` с TTL в памяти процесса. Для одного инстанса достаточно; при масштабировании пересаживается на Upstash за час.

**Проблема.** Один канал уведомлений может лечь — Telegram Cloud, SMTP-провайдер. Терять заявку недопустимо, она стоит денег.

**Решение.** `Promise.allSettled` на оба канала: если доставился хотя бы один — считаем успехом. В лог пишем только имена упавших каналов и коды ошибок — без содержимого заявки и без токенов, иначе PII и секреты утекут в логи хостинга.

**Проблема.** Nodemailer в текстах ошибок раскрывает SMTP-адреса и часть учётных данных.

**Решение.** Обёртка перехватывает исключение и пробрасывает только `error.code` (`ETIMEDOUT`, `EAUTH`) в новом `Error("smtp: <code>")`. Оригинальный `cause` наружу не идёт.

### 8. SEO и техническая база

- `sitemap.ts` и `robots.ts` через App Router, не статические файлы;
- `opengraph-image.tsx` — динамическая OG-картинка с брендовыми шрифтами (Golos и Unbounded в `.woff`);
- JSON-LD (`Course`, `EducationalOrganization`, `FAQPage`) собирается хелпером и вставляется в `<head>`;
- Яндекс.Метрика с целями `leadSubmit`, `telegramClick` и т.д.

**Проблема.** Юридические страницы обязательны по 152-ФЗ, иначе форма заявки нелегальна. Но содержание требует ФИО и ИНН преподавателя, которых на момент разработки ещё не было.

**Решение.** Плейсхолдеры `[ИМЯ]`, `[ГОД]`, `[ФИО]`, `[ИНН]` оставили как есть в исходниках — заказчик подставит их перед публикацией через find-and-replace. Компонент `LegalStub` показывает список того, что нужно заполнить.

### 9. Доступность и производительность

- `scroll-behavior: smooth` на `html`, но с `prefers-reduced-motion` — отключается;
- `:focus-visible` рисуется только при навигации с клавиатуры, при клике мышью не появляется;
- шрифты — через `next/font` без FOUT, preload только критичных;
- формы: `autoComplete`, `inputMode="tel"` — мобильная клавиатура открывается правильная;
- `aria-invalid`, `aria-describedby` на всех полях, ошибки в `role="alert"`.

**Проблема.** Чекбокс согласия — с кастомным дизайном (квадратик с жёсткой обводкой и «нарисованной» галочкой). Родной `<input type="checkbox">` при этом должен остаться доступным.

**Решение.** Родной `input` позиционируется поверх декоративной коробки: `appearance: none`, `opacity: 0`. Клавиатура и скринридеры видят обычный чекбокс, глаза — стилизованный. Галочка рисуется через `peer-checked:opacity-100` — CSS-only, без JS-состояния.

### 10. Процесс работы команды

Настроили процесс так, чтобы правки контента не требовали разработчика: копирайтер работает в `src/lib/*.ts`, дизайнер меняет токены в `globals.css` — они автоматически подтягиваются во все секции, фронтенд трогает только компоненты.

**Проблема.** Ветки копирайтера и разработчика часто рассинхронизировались, конфликты в `data.ts` были каждую неделю.

**Решение.** Развели репозитории по remote'ам и разделили «полосы ответственности» в файлах. Контент летит через один remote, код — через другой; регулярный `fetch` обоих и мерж через PR. Конфликты стали редкостью.

## Результат

Одностраничник с пятью интерактивными блоками, доставкой лидов по двум каналам, тремя слоями защиты от спама без капчи, полной SEO-разметкой и юридической базой под 152-ФЗ. Дизайн-система из 30 строк CSS без плагинов — поддерживает один человек.

**Ключевые архитектурные решения:**

- одна Zod-схема на клиент и сервер — валидация не расходится;
- контент как типизированные данные — методист правит без разработчика;
- rate-limit без Redis — на текущем масштабе не нужен, пересаживается за час;
- три слоя антиспама без капчи — конверсия не теряется.

**Следующая итерация:** A/B-тест первого экрана, аналитика скролла и heatmap, фиксированная кнопка CTA на мобильных.
